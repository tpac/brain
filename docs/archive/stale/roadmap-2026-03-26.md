## What Was Built (Session 15) — The Foundation

### The Challenge System (SHIPPED, v7.0.0, 250 tests)

**What:** Every recall injection is now framed as an assertion to challenge, not a fact to absorb. Claude sees an action menu:
- ✅ Agree — still accurate
- ✏️ Revise — update with `revise(node_id, content, reason)`
- ❌ Disagree — wrong/outdated
- 📝 Encode new — topic not covered

**Why it matters:** Agent A/B experiments proved this was THE single biggest driver of revision behavior. Without the menu, every agent defaulted to AGREE on everything. With it, agents called 5-11 tools to actually encode and revise.

**How it works:**
```
Stop hook → auto_encode() detects signal (decision/correction/insight)
         → store_exchange() saves Tom's message WITH signal annotation
         → message_stream table in brain_logs.db

Idle     → detect_consolidation_candidates() finds duplicate nodes
         → expire_old() resolves messages > 48h

Recall   → get_actionable() returns pending messages with escalation level
         → recall_with_embeddings() returns nodes with _gap if nothing found
         → BrainVoice.render_prompt() assembles:
             - Challenge header with action menu
             - Recalled nodes with full IDs, revised:never status, confidence
             - Gap callouts (🔴 UNKNOWN TOPIC)
             - Consolidation pairs (when < 2 recall results)
             - Pending Tom messages with escalation tiers

Encode   → remember() or revise() marks recent pending as resolved
         → resolve_recent_pending() is the SINGLE ENTRY POINT
```

### The Pending Message Lifecycle (SHIPPED)

**What:** Tom's messages are captured invisibly on every Stop event, surfaced chronologically as a "journey" on recall, escalate over turns if not encoded, and expire after 48h.

**Why it matters:** The agent experiments showed that pending messages showing Tom's 3-message progression (explore → refine → decide) was what gave encoding QUALITY. Agents saw the journey and understood WHEN to encode (at the decision), WHAT to encode (the final design), and HOW (one rich node with journey as rationale, not 3 separate thin nodes).

**Escalation model:**
- `pending` (surfaced ≤ 2 times) — gentle: "[BRAIN] PENDING"
- `attention` (surfaced 3-4 times) — pressure: "⚠️ ATTENTION"
- `urgent` (surfaced 5+ with decision/correction, OR 7+ any) — red alert: "🔴 NEEDS IMMEDIATE ATTENTION"

**Key architecture decision:** `resolve_recent_pending()` in brain_surface.py is the SINGLE ENTRY POINT for marking messages as encoded. Any future encoding path (vocabulary, corrections, new types) calls this one method. Tom explicitly asked for this reusability.

### revise() — Encoding IS Updating (SHIPPED)

**What:** First-class MCP tool. Appends content with revision divider, re-embeds, re-indexes TF-IDF, regenerates summary, auto-resolves consolidation pairs.

**Why it matters:** The brain had 83% stale nodes (never revised, old). Before revise(), the only option was creating new nodes — leading to duplication. Now Claude can update existing knowledge in place. The challenge system shows `revised:never` on every node, making staleness visible and actionable.

### Key Experimental Findings

**The 7-condition isolated variable experiment:**

We tested each format feature independently. Same Tom message, same recalled nodes, same 4 questions. Only ONE variable changed per condition.

| Condition | Changed from baseline | Revision actions | Tool calls |
|---|---|---|---|
| A: OLD baseline | Nothing | 0/5 | 0 |
| B: +Full content | No truncation | 0/5 | 0 |
| C: +Full IDs | 32-char IDs | 0/5 | 0 |
| D: +Revised status | "revised:never" shown | 0/5 | 0 |
| E: +Challenge header | Action menu (✅✏️❌📝) | **1/5** | 0 |
| F: +Pending messages | Tom's unencoded msgs | 0/5 | 0 |
| G: Full NEW | Everything combined | **1/5** | **5-11** |

**Finding: Three features drive encoding behavior. Everything else is enablers.**
1. **Pending messages showing the journey** → encoding QUALITY
2. **Action menu (✅ ✏️ ❌ 📝)** → encoding HAPPENS
3. **Red alert escalation** → encoding happens NOW

Full content, full IDs, revised status, confidence scores, neighbor context — all useful but NOT what changes behavior. The framing changes behavior.

**The 3-turn decision simulation:**

Tom explored a topic across 3 turns, then said "Ship it." The agent with NEW format:
- Actually called 11 tools (created node, revised existing node, enriched with 4 vectors)
- Said: "The journey is represented by the new node's rationale, not as separate nodes. The path was convergent — no dead ends worth preserving independently."
- Made an editorial judgment about WHAT to encode — not just that encoding should happen

The agent with OLD format said "I would encode" but made 0 tool calls.

## Priority 1: Recall Quality — The 93% Problem (NOT STARTED)

### The Problem

93% of nodes are NEVER recalled across 30 diverse queries. Only 56 out of 755 active nodes appeared. 5-7 "hub" nodes dominate every query:

| Node | Appearances | Why it dominates |
|---|---|---|
| "Solution fixation — reframe" | 7/30 | General principle, broad embedding match |
| "Verify against ORIGINAL" | 7/30 | "code" + "changes" match everything |
| "Recall brain before designing" | 5/30 | "brain" + "eval" are everywhere |
| "Produce documents alongside code" | 5/30 | Broad content, high activation |
| "HOOKS-ARCHITECTURE.md" | 4/30 | 1600+ chars = matches any hook query |

### Root Causes

1. **Hebbian reinforcement feedback loop** — hub nodes get recalled → accessed → score higher → recalled more. Rich get richer.
2. **Broad content = broad embedding match** — a 1600-char node about everything hooks do matches ANY hook query, crowding out the specific node that actually answers the question.
3. **Locked nodes never decay** — 80% locked means 587 nodes compete equally regardless of age or relevance. A week-1 decision has the same permanence as yesterday's correction.
4. **RELEVANCE_FLOOR (0.80) too low for broad nodes** — specific queries still get broad matches above 0.80.

### Impact

The challenge system is working on the wrong nodes. If recall surfaces "Solution fixation" for "How does the DAL work?", the challenge menu asks Claude to Agree/Revise on a node that's irrelevant to the question. The format is perfect — the content is wrong.

### Potential Approaches

**A. Hub dampening** — Nodes with access_count > 50 get a score penalty (e.g., multiply by `1 / log(access_count)`). This is the simplest fix — reduce the rich-get-richer loop. The scoring formula is in brain_recall.py STEP 6.

**B. Query-specific relevance** — Instead of one embedding per node, use the multi-vector enrichment (Q/A/B/K) more aggressively. The enrichment vectors were designed for this — the "question" vector should match the query better than the broad content vector.

**C. Dynamic RELEVANCE_FLOOR** — Raise the floor for nodes with very high access_count. If a node has been accessed 100 times, require 0.85+ similarity instead of 0.80. This makes hub nodes compete harder.

**D. Recency boost at scoring** — Nodes created/revised recently get a multiplier. This exists partially (`recency_score`) but may not be strong enough. Fresh knowledge should beat stale knowledge.

**E. Diversity enforcement** — After selecting top results, ensure they're from different clusters/types. If 3/5 results are all rules, replace 1-2 with other types. This prevents type domination.

**Hint for implementation:** The scoring formula lives in brain_recall.py, STEP 6 (blended score calculation, lines ~850-890). The hub dampening approach (A) is a one-line change: `score *= 1.0 / max(1, math.log(access_count + 1))`. Test with the 30-query simulation and measure: does the top-7 hub domination decrease? Do different nodes appear?

**Benchmark FIRST:** Run `eval/decode_funnel.py` before ANY change. Baseline: 51% top-3, 69% top-8. Changes must not regress.

## Priority 2: In-Memory Graph (NOT STARTED)

### The Problem

Every recall does full SQLite scans — embedding cosine against all 755 nodes, TF-IDF against all vectors, neighbor lookups via SQL JOINs. Total: ~300ms. Fine now, but:
- At 2000 nodes: ~800ms
- At 5000 nodes: too slow for the 9-second hook timeout
- Graph traversal (neighbor exploration) requires separate SQL queries per hop

### The Vision

Load the full graph into Python dicts + numpy arrays at daemon startup:
```python
class InMemoryGraph:
    embeddings: np.ndarray          # (N, 768) matrix — one cosine scan
    node_ids: List[str]             # index → node_id mapping
    node_data: Dict[str, Dict]     # node_id → full node dict
    edges: Dict[str, List[Tuple]]  # node_id → [(neighbor_id, relation, weight)]
```

Benefits:
- Cosine similarity: numpy matrix multiply, ~1ms for 5000 nodes
- Neighbor lookup: dict access, O(1)
- Graph traversal: Python iteration, no SQL roundtrips
- Recall pipeline shrinks from 400 lines to ~50

### Why It Matters

Session 15 proved: "Let me read the graph, not query it." When I read all 732 nodes, I found 4 meta-patterns no single node contained. The in-memory graph enables:
- Subgraph retrieval: "give me the 2-hop neighborhood of this node"
- Cluster detection: community algorithms on the Python graph
- Path traversal: follow `evolved_from` chains without SQL
- Real-time pattern matching: "you're approaching a problem shape I've seen before"

### Hint for Implementation

The daemon already holds a Brain instance in memory (`daemon_server.py`). The graph loads at daemon startup alongside the Brain. The `recall_with_embeddings()` pipeline uses the in-memory data instead of SQL. The DAL layer still handles writes; the in-memory graph is read-only and refreshed periodically or on write notification.

Start with embeddings only (numpy matrix). Then add edges (dict). Then add traversal methods. Each step is independently useful and testable.

**Dependency:** None. Can start anytime. But recall quality (Priority 1) should be fixed first — loading a bad scoring formula into memory just makes it bad faster.

## Priority 6: Error Log Lifecycle (NOT STARTED)

### The Problem

The consciousness layer surfaces URGENT errors from `debug_log`. But errors persist forever — even after the underlying code is fixed. Session 15's agent found "n.archived bug" and "hour must be in 0..23" as current bugs, but both were already fixed in the code. The brain told the agent they were broken when they weren't.

### Impact

Every future session starts with stale error alerts. Claude wastes time investigating bugs that are already fixed. Trust in the URGENT signals degrades — "these are probably old."

### The Fix

Same lifecycle pattern as pending messages:
- Errors get a `resolved` flag
- When code is deployed (daemon restart with new fingerprint), old errors are marked resolved
- Consciousness only surfaces unresolved errors from the current code version
- Or simpler: TTL-based expiry — errors older than 24h are not surfaced as URGENT

### Hint for Implementation

The `code_fingerprint` already exists on daemon ping. Compare the fingerprint when surfacing errors: if the error was logged under a different fingerprint, it's from old code — don't surface as URGENT. Show as historical context instead.

## Priority 8: Graph Pattern Detection (NOT STARTED, HIGHEST CEILING)

### The Vision

Session 15's biggest insight: reading 732 nodes and finding 4 patterns that lived in the CONNECTIONS, not in any individual node. This should happen automatically.

The algorithm:
1. Find nodes with high embedding similarity but no edge (should be connected)
2. Find nodes that share many neighbors but aren't connected (triadic closure)
3. Present clusters to Claude: "These 5 nodes tell a story together. What's the pattern?"
4. Claude articulates the pattern — that IS the new knowledge
5. Store as a pattern node connected to all cluster members

### Why It Has the Highest Ceiling

Every other priority improves existing features. This one creates NEW KNOWLEDGE that doesn't exist anywhere. The 4 patterns from Session 15 were genuinely new — Tom said "you're the only one working on this code with me" and finding those patterns made the entire session more productive.

### Hint for Implementation

Start simple: in idle_maintenance, pick 10 random nodes with high embedding similarity but no intentional edge. Group them. Surface the top cluster to Claude at boot with: "These nodes seem related but aren't connected. What's the pattern?" Claude's response IS the new node.

This requires the in-memory graph (Priority 2) for efficient similarity computation. Build Priority 2 first.

1. **Slow down.** "No one is chasing you, I have unlimited tokens." I rush, skip verification, introduce bugs. Every session.

2. **Check yourself.** Verify function signatures before calling. Verify columns exist. Verify imports. I called `_store_tfidf_vector` with 2 args when it takes 4. FK errors from short IDs.
